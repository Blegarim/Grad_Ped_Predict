## How to read this

Each **model** gets one block: a run register (which run dirs fill which cells), the **2×2 cross-protocol
matrix** (train × test over {anchored, streaming}), and the **G-decomposition** of the anchored→streaming
crossing-detection gap.

- **Cells report crosses-only** (the thesis task). Format per cell: `AUC · raw-F1 → tuned-F1`.
  - **AUC** = threshold-free ranking ability (the *diagnostic*).
  - **raw-F1** = F1 at the default 0.5 threshold (the "before recalibration" operating point).
  - **tuned-F1** = F1 at the val-tuned F1-optimal threshold (the "after recalibration" point — the **only
    reportable** threshold-tuned number, per the M2 val-never-test rule). `oracle_*` same-split sweeps are
    excluded on purpose.
- **G-figures** are measured in **tuned-F1 on the test=streaming column** (F1 is the currency recalibration
  acts on; AUC is the explanation, never quoted *as* a G). All three are deltas of the two anchored→streaming
  numbers plus the streaming-trained number:
  - `G_total   = (streaming-trained, streaming-test, tuned-F1)  −  (anchored-trained, streaming-test, RAW-F1)`
  - `G_prior   = (anchored-trained, streaming-test, tuned-F1)   −  (anchored-trained, streaming-test, RAW-F1)`  ← recalibration-fixable part
  - `G_hardneg = (streaming-trained, streaming-test, tuned-F1)  −  (anchored-trained, streaming-test, tuned-F1)`  ← residual hard-negative skill gap
  - By construction `G_total = G_prior + G_hardneg`.

### Caveat: train and test differ in what their negatives are made of

Measured 2026-08-20 (negative-composition report, now archived). The streaming
splits are not two samples of one distribution:

| Split | positive | never crosses | will cross, later | already crossed |
|---|---|---|---|---|
| train | 2.9% | 64.3% | **25.7%** | 7.2% |
| val | 2.8% | 77.5% | **15.2%** | 4.6% |
| test | 3.1% | 53.4% | **39.2%** | 4.3% |

The test split carries half again as many "will cross, just not yet" windows as train, and val carries
far fewer than either. So a train-to-test drop is **not purely a generalisation gap** — the test set is
structurally harder in the exact way this thesis is about, and val is the *easiest* of the three, which
also makes val-tuned thresholds optimistic for test in a way the M2 rule does not correct. Applies to
every streaming column below; the anchored columns are unaffected (different windowing entirely).

confound-free measurement. A sampler-matched re-run of the anchored half would settle it.

## Reading of the two models together

Both models agree on the headline: **G_prior ≈ 0, G_hardneg ≈ G_total**, and in both, a model trained on the
anchored benchmark drops to near-chance ranking (AUC ~0.53) when tested on the streaming stream. **Of the
anchored→streaming deployment gap, ~0% is recalibration-fixable and ~100% is a genuine hard-negative skill
gap** the anchored benchmark never trains.

What Model B adds, stated precisely: it shows the gap is **not an artifact of the multi-task heads** — with
only the crossing head trained, the same collapse appears. It is *not* an independent confirmation of the
magnitude, because of the sampler mismatch above. Quote Model A's numbers; cite Model B for the
no-multi-task-interference point.

**Caveats that must ship with these numbers (do not bury):**
1. **Data-volume confound.** The anchored training set is ≈4.9k windows; the streaming one is ≈88k, about
   18× larger. So `G_hardneg` currently mixes together *what protocol the model trained on* and *how much
   data it trained on*. Phrase findings as "consistent with a hard-negative gap," not "proven." The clean
   test is a streaming run subsampled to ≈4.9k windows — matched size, same protocol.
2. **F1 is unstable at a 1-in-37 base rate.** A handful of samples moving across the threshold swings it.
   The AUC reading (0.88 → 0.53, both models) is the more trustworthy number today; average-precision and
   precision-at-fixed-recall are the sharper replacements (Stage 6).
3. **Model B's sampler mismatch** (register footnote †) — the anchored half trained without the oversampler,
   the streaming half with it. Settle it with a sampler-matched re-run of the anchored half before Model B's
   magnitude is quoted anywhere.
4. **Single seed.** Every cell here is `seed=42`, one run. The multi-seed protocol (screen with one, confirm
   with three, report mean±spread) has not been applied to any of these numbers.

**How these numbers are used now (August 2026 reframe).** The decomposition has moved from *the thesis
result* to *the thesis motivation* — it establishes that the problem is real and that recalibration cannot
solve it, which is what justifies building a method. Practically this **lowers** the bar on caveat 1 (a
motivating measurement can carry an acknowledged confound) and **raises** it on caveats 3 and 4, because any
new method will be compared against these runs as baselines — and a baseline with an accidental
configuration difference invalidates the comparison, not just the caveat.

## Onset-arm runs (R1–R4) — how their matrix is filled

Decided 2026-09-16, before any onset run has eval numbers. The onset head changes what a 2×2 can mean,
so the rule is written down before the first cell is filled.

**The anchored-trained row is shared, not re-run per method.** An onset model cannot be *trained* on
anchored data: benchmark windows are generated without the three onset fields (`window_track_benchmark`
never computes them), and the hazard loss refuses to run without them (`data/onset_target.py::_require`
raises `KeyError`). So every onset run takes its anchored-trained row from **one** no-onset reference —
the anchored leg of **R2** (`pose_baseline`), trained with flags identical to its streaming leg. Say so in
each register entry: that row is the baseline trained on anchored data, not the method.

Adding onset fields to anchored windows would make anchored *training* possible, but it is a design
change, not a fix: every anchored positive starts crossing 30–60 frames out (`benchmark_tte_min/max`),
while the readout is pinned to ≤32 frames (`onset_horizon == future_offset + tol`), so the pure and hedge
arms would be trained to call almost every anchored positive negative. Deferred as a possible ablation.

**The streaming-trained row gets both test columns from the stock `evaluate.py` — no workaround.**
Verified in code 2026-09-16: evaluation never computes a loss and never builds onset targets
(`eval/evaluate.py::evaluate_model` is forward → `MetricAccumulator.update` → threshold sweep); the reader
emits only the onset fields a chunk has (`data/lmdb_dataset.py`), collation silently omits fields that no
sample carries (`data/collate.py`), and the accumulator reads labels by task name only
(`training/metrics.py`). The onset fields feed the *training* loss and nothing else. Not yet exercised
end-to-end on real anchored chunks — R1's anchored evaluation is the first run of that path.

**Which output each run is scored on:**

| Run | `onset_report_crosses` | Scored output | Horizon |
|---|---|---|---|
| R1 `pose_onset_aux` | false | `crosses_frame` — the same head as the baselines | — |
| R3 `onset_pure`, R4 `onset_hedge` | true | `crosses_readout` = P(onset ≤ 32 frames) | 32, on **both** test protocols |

A hazard head can also be read at the anchored protocol's own horizon (≈60 frames). That answers a
question the fixed-horizon baselines cannot, so it **never goes in a matrix cell**; if reported at all it
is a separate, labelled column (and needs a small eval-side addition).

**Shape of an onset run's matrix:**

| | test = anchored | test = streaming |
|---|---|---|
| **train = anchored** | shared: R2 anchored leg | shared: R2 anchored leg |
| **train = streaming** | this run's checkpoint — anchored val → test | this run's checkpoint — streaming val → test |

G-figures use the usual arithmetic with the shared row. **Never train an onset recipe through
`run_arm.py`** — its anchored leg fails on the missing fields and the runner is fail-fast. Evaluate an
onset checkpoint on the eval cells with `run_arm.py --skip-train --checkpoint <run>/checkpoints/best.pth`,
or with `evaluate.py --set data.protocol=anchored` (val, then test) when the streaming cells already exist.

R1 finished (early-stopped after epoch 28; best epoch 8) and was scored on both protocols. **Test, at
val-tuned thresholds, against its no-onset partner `20260714_134253`** (both streaming-trained, one seed):

| test | R1 `pose_onset_aux` | `20260714_134253` |
|---|---|---|
| streaming | 0.772 · 0.232 → **0.225** | 0.784 · 0.249 → **0.225** |
| anchored | 0.706 · 0.373 → **0.479** | 0.679 · 0.258 → **0.428** |

(`AUC · F1@0.5 → tuned F1`.) The auxiliary head left the reported streaming number unchanged. R2's anchored
leg `20260917_072445` reproduced the older anchored-trained run closely (anchored test AUC 0.883 vs 0.880;
streaming test 0.538 vs 0.529), so the machine change is not what moves these numbers.

**Two diagnostics on R1's own checkpoint** (`outputs/diagnostics/r1`, from
`dump_onset_predictions.py` plus two archived report scripts; each reproduced R1's stored eval row before
reporting anything):

* **The onset head carries timing, and the binary head partly does too.** Streaming test mean score by true
  onset group falls monotonically — 0–15 frames 0.38, 16–31 0.32, 32–63 0.27, 64–95 0.15, ≥96 0.07, no
  crossing seen 0.05 — and per-horizon AUC degrades with the horizon (H=16 0.79 → H=96 0.73). Crossers
  within 32 frames vs **later** crossers is AUC ≈ 0.74, vs never-seen-crossing ≈ 0.80: the hard negative is
  hard, as the streaming brief argued. R1's readout (never selected on) edges its own `crosses_frame`:
  test AUC 0.775 vs 0.772, tuned F1 0.232 vs 0.225.
* **"Frozen" backbone, measured.** Weights are genuinely unchanged (max param diff 0.0), but the BatchNorm
  running statistics drift (median layer mean-shift 0.06 sd, stem conv variance to ~8% of pretrained).
  Re-estimating those statistics from different sampler draws — changing no weight — moves val AUC
  0.788–0.809 and val F1@0.5 0.208–0.234. **That is the same size as the differences between arms above**,
  which is the honest reason R1-vs-baseline cannot be called either way from one seed. Restoring the
  pretrained statistics drops val AUC to 0.702 (the trained head depends on the drifted features — not
  evidence about the fix). **No re-estimation reproduced an "everything is a crossing" epoch**, so those
  epochs are *not* established to come from BN drift; their cause is still open. Recipe v2
  removes the drift and the seed-count limit; it does not claim to fix them.

`20260919_111158_pose_full_onset_hedge`, v1 recipe + `onset_readout_weight=0.5`, streaming-trained, seed 42.
Early-stopped at **epoch 20** (best epoch 5; `early_stop_patience=15`). Scored on `crosses_readout`.

| test | AUC | raw F1 | tuned F1 | threshold |
|---|---|---|---|---|
| streaming (n=69,875) | 0.7757 | 0.1894 | **0.1847** | 0.40 |

**The hedge did not help.** On streaming its tuned F1 (0.185) is the WORST of the four arms (baseline 0.225,

**Why this is GOOD for the thesis rather than bad.** The obvious objection to an onset-timing claim is
*"this is just multi-task learning — the binary term is doing the work."* R4 is the arm that adds a
fixed-horizon binary CE back on top of the hazard objective, and it is **worse than the pure arm**. So the
arm that wins on detection latency (R3) is the one with **no crossing cross-entropy at all**, and the
objection does not apply to the headline.

| FA/hr | binary head (R1 `crosses_frame`) | **R3 pure** | R4 hedge |
|---|---|---|---|
| 1200 | 62.0% @ 5.31s | **66.8% @ 6.15s** | 49.8% @ 4.42s |

**R4 is worse than BOTH pure arms at every budget.** Pure timing wins; pure binary is middling; the mixture

## R3C `onset_pure_censored` — the premise test (2026-09-20)

`20260920_021440_pose_full_onset_pure_censored`. **Identical to R3 in every flag**; the sole difference is
`paths.lmdb_train` gaining `preprocessed_train_censored` — the **7,470** M4-censored windows (8.5% of the
split) that carry no honest binary label and that only the hazard formulation can consume. Ran 19 epochs,
best epoch 4 (patience 15).

**Window metrics — indistinguishable from R3, as expected:** streaming test AUC 0.7550 / raw F1 0.2214
(R3: 0.7610 / 0.2222).

**Detection-latency — R3C trades detection rate for LEAD TIME:**

| FA/hr | binary (R1) | R3 pure | **R3C +censored** |
|---|---|---|---|
| 1200 | 62.0% @ 5.31s | **66.8%** @ 6.15s | 65.4% @ **7.92s** |
| 460 | 34.6% @ 3.11s | **56.6%** @ 4.22s | 45.9% @ 4.30s |
| 205 | 22.9% @ 2.83s | **48.8%** @ 3.05s | 31.2% @ 3.00s |
| 95 | 14.1% @ 2.16s | **41.5%** @ 2.11s | 19.0% @ **3.01s** |
| 41 | 5.9% @ 0.92s | **34.1%** @ 0.77s | 12.2% @ **2.34s** |

**Reading, stated plainly: the censored windows did NOT improve the headline metric.** R3 remains the best
arm. But R3C is not simply worse — it warns substantially earlier (2.34s vs 0.77s at 41 FA/hr, 3x the lead;
3.01s vs 2.11s at 95) while catching fewer. Plausibly mechanistic: censored windows are all late-track,
truncated-future examples, so training on them as censored observations pushes the model to commit earlier
under uncertainty. **R3C still beats the binary baseline at every budget**, so the timing formulation itself
is not in question — the extra data changed WHAT it optimises for.

**Confound:** R3C's `best.pth` is epoch 4, the earliest of any arm, selected on the noisy F1@0.5 right at
the warmup boundary. Part of the detection deficit may be an undertrained checkpoint.

**Collapse epochs — the one unambiguous win.** R3C collapsed on epochs **1, 2 only**, against 1/2/4/13/17
for both R3 and the v1 baseline (R4: 1/2/4). Adding 7,470 windows reshuffled the sampler draw order and
eliminated all three later collapses. Combined with the earlier finding that collapse epochs are identical
across completely different objectives, this establishes the instability as **sampler/data-order driven**,
not model- or loss-driven.

**AP does NOT generalise as a selection metric.** On three arms AP was the only window metric matching the
detection ranking; on four it fails — AP puts R3C (0.1488) below the binary head (0.1547) while R3C beats
it at every budget. Do not adopt `selection_metric=crosses_ap` on that evidence.

## Adding a new run (do this every eval pass)

1. Run `evaluate.py --split val` then `--split test` on **both** protocols so all four cells exist.
2. Pull `crosses_auc`, `crosses_f1` (raw), `tuned_crosses_f1` from `eval_log.csv` (test rows only).
3. **Diff the config against its partner leg before filling any cell.** A 2×2 is only a comparison if the
   two training runs differ in the training protocol and nothing else. Compare the two
   `resolved_config.yaml` files and record any difference in the register — this is exactly the check that
   would have caught the Model B sampler mismatch in July instead of a month later:
   ```
   diff outputs/runs/<anchored_run>/resolved_config.yaml outputs/runs/<streaming_run>/resolved_config.yaml
   ```
   Expect exactly one difference (`data.protocol`). Anything else is either a bug to fix or a caveat to
   write down, and it must be resolved *before* the G-figures are computed.
4. Add the run to the register; if it completes/extends a model's 2×2, fill the matrix + recompute the
   three G-figures with the arithmetic shown above.
5. Regenerate the machine table: `python -c "from pedpredict.utils.logging import rebuild_index; rebuild_index('outputs/runs')"`.
6. Bump **Last updated**.
